# E7 Browser Debugging Evaluation

Status: evaluation complete; no LocalSpace Browser Pack implemented.

Decision date: 2026-07-21.

## 1. Decision

LocalSpace will not implement a first-party Browser Pack in the current v1.1
roadmap.

The recommended integration model is:

1. Use Playwright CLI plus a progressively disclosed Skill for routine browser
   verification performed by coding agents.
2. Use an external Playwright MCP server when a task genuinely benefits from a
   persistent browser context, rich accessibility snapshots, or a long-running
   exploratory automation loop.
3. Use the external Chrome DevTools CLI or MCP server for Chrome-specific
   console, network, performance, Lighthouse, source-map, and heap debugging.
4. Reconsider a LocalSpace Browser Pack only after real project evidence shows
   that these upstream tools cannot satisfy LocalSpace workflows without unsafe
   or materially inefficient glue code.

This is an architecture decision, not a declaration that LocalSpace currently
supports browser automation. No browser tools are added to the LocalSpace Tool
Catalog or default MCP surfaces by E7.

## 2. Evidence

### 2.1 Playwright

The official Playwright MCP project explicitly distinguishes coding-agent use
from persistent agentic browser loops:

- it recommends CLI plus Skills for coding agents because the CLI avoids loading
  large MCP schemas and verbose page snapshots into the model context;
- it retains MCP for workflows where persistent state and rich iterative page
  introspection justify the larger context and lifecycle cost.

The official Playwright CLI is designed for coding agents, supports browser
actions, snapshots, screenshots, code generation, and installable Skills.

References:

- <https://github.com/microsoft/playwright-mcp>
- <https://github.com/microsoft/playwright-cli>

### 2.2 Chrome DevTools

The official Chrome DevTools project already provides both MCP and CLI access to
live Chrome debugging. Its upstream implementation covers capabilities that
would be expensive and security-sensitive for LocalSpace to duplicate:

- browser automation and screenshots;
- console and source-mapped errors;
- network request and response inspection;
- performance traces and actionable insights;
- Lighthouse audits;
- persistent or isolated browser profiles;
- a three-tool `--slim` MCP mode for basic browser tasks.

The Chrome DevTools CLI reuses a background daemon and browser instance, returns
human-readable or JSON output, and therefore fits LocalSpace's existing
`exec_command` and `write_stdin` process model without adding browser schemas to
the core Tool Surface.

References:

- <https://github.com/ChromeDevTools/chrome-devtools-mcp>
- <https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/cli.md>

## 3. Option comparison

| Option | Context cost | Implementation burden | Security surface | Browser depth | Current decision |
| --- | --- | --- | --- | --- | --- |
| Playwright CLI + Skill | Low and progressive | Low | Uses existing command policy | Strong routine automation | Adopt for normal coding workflows |
| External Playwright MCP | Higher fixed Tool Schema cost | External | Separate MCP lifecycle and policy | Strong persistent exploration | Optional specialist integration |
| Chrome DevTools CLI/MCP | CLI low; MCP medium/high | External | Browser content and debugging data are exposed to the selected client | Strong Chrome debugging and performance analysis | Optional specialist integration |
| LocalSpace Browser Pack | High unless aggressively partitioned | High and ongoing | Would add origins, profiles, uploads, downloads, credentials, browser processes, and remote-debugging controls | Potentially strong but duplicative | Reject for current roadmap |

## 4. Why LocalSpace should not duplicate upstream browser runtimes

LocalSpace's core value is secure access to approved local development
workspaces. A first-party Browser Pack would introduce a second major resource
domain with substantially different lifecycle and trust requirements:

- browser binaries and version compatibility;
- browser context and profile ownership;
- authentication cookies and personal session data;
- arbitrary external origins;
- file uploads and downloads;
- screenshots, page content, headers, and network bodies;
- remote-debugging ports and browser daemons;
- browser sandboxing and cleanup after abnormal termination.

Playwright and Chrome DevTools already maintain these concerns. Reusing their CLI
or MCP interfaces avoids duplicate implementation while allowing LocalSpace to
retain command approvals, process concurrency, activity logs, audit logs, and
workspace-scoped output review.

## 5. Required boundaries for a future Browser Workflow Skill

A later Skill may teach the MCP host how to invoke an installed upstream browser
CLI, but it must not imply that LocalSpace bundles or guarantees that CLI.

The first Skill version must require:

- localhost targets by default;
- an explicit allowlist before accessing external origins;
- an isolated browser context or profile by default;
- no reuse of the user's daily browser profile or login state;
- screenshots, traces, generated tests, and downloads written only to an
  approved workspace path or bounded temporary directory;
- explicit path validation before upload;
- LocalSpace command approval remaining authoritative;
- no automatic remote-debugging connection to an arbitrary existing browser;
- cleanup instructions for persistent CLI daemons and browser sessions;
- clear unsupported output when the upstream CLI is not installed.

The Skill should prefer Playwright CLI for ordinary UI-flow verification and
direct the host to Chrome DevTools only for debugging needs that Playwright does
not cover well, such as performance traces, Lighthouse, detailed network
analysis, or Chrome-specific runtime inspection.

## 6. Reconsideration gate

A LocalSpace Browser Pack may be reconsidered only when all of the following are
available:

1. At least three real LocalSpace front-end tasks where CLI plus Skill was
   materially insufficient.
2. A written capability gap that cannot be solved by external Playwright or
   Chrome DevTools MCP integration.
3. A policy model covering origins, profiles, uploads, downloads, remote
   debugging, secrets, and browser lifecycle.
4. A bounded Tool Pack design that leaves the default Tool Surface unchanged.
5. Automated real-browser tests on supported operating systems.
6. A maintenance and release plan for browser dependencies and security fixes.

Until this gate is met, Browser Pack implementation remains out of scope.

## 7. E7 acceptance result

- Official Playwright CLI/MCP boundaries reviewed.
- Official Chrome DevTools CLI/MCP boundaries reviewed.
- Three integration approaches compared.
- Security and lifecycle costs documented.
- LocalSpace Browser Pack rejected for the current roadmap.
- External tools and a future thin Skill selected as the preferred architecture.
- No runtime, package dependency, Tool Catalog, or default Tool Surface change.
- Real browser acceptance is not applicable because E7 is evaluation-only.
