本计划用于指导 LocalSpace 在现有稳定架构上增强 ChatGPT 编程效率、工具契约一致性、性能可观测性、受控并发和后续高级代码能力。

任何阶段只有在代码、测试、文档和真实 MCP 客户端验收一致后，才能描述为 `supported`。仅完成设计、本地实现或自动化测试时，必须准确注明实际边界。

---

## 2. 背景与当前判断

LocalSpace 当前已经具备完整的常规单仓库编程闭环：

- 工作区和受控根目录；
- 项目指令与 Agent Skills；
- 文件读取、搜索和目录导航；
- TypeScript/JavaScript 轻量符号、导入和引用扫描；
- Codex 风格补丁修改；
- 长进程、PTY 和进程轮询；
- Git 状态、Diff、Stage、Commit 和 Log；
- aggregate changes 展示；
- OAuth、敏感路径保护、高风险命令审批和审计日志；
- checkout 和 managed worktree 模式；
- stateless MCP 重启恢复。

当前主要差距不在于缺少基础文件工具，而在于：

1. 实际注册工具、服务器指令、文档和 Skill 存在漂移；
2. 尚不能准确区分 ChatGPT、网络、MCP 固定成本和工具执行成本；
3. 多个已知文件仍需多次 MCP 往返读取；
4. 多项独立验证仍需串行启动和轮询；
5. LocalSpace 服务端没有显式的有界并发调度和状态锁；
6. 大型重构缺少完整语言服务语义；
7. 前端任务缺少浏览器反馈闭环；
8. 项目级权限策略和确定性自动化仍较有限。

本路线优先解决正确性、可观测性和往返效率，不以扩大默认工具数量为目标。

---

## 3. 产品目标

LocalSpace 应继续保持以下定位：

> ChatGPT 或其他 MCP 主机直接、显式、安全地调用本地编程工具，而不是在本地运行一个不可见的自治 coding agent。

本路线的目标是：

- 使常规单仓库开发效率进一步接近 Codex 和 Claude Code；
- 减少无效工具选择和不必要的 MCP 往返；
- 对读、写、Git 和进程工具建立确定性的并发语义；
- 保持默认 `hybrid` 工具面有界；
- 将高级能力按可选工具包渐进披露；
- 保持所有写操作、安全审批和用户可见 Diff 可审查；
- 为性能优化建立可重复的基准，而不是凭感觉判断；
- 保证旧配置和既有核心工作流不因增强路线被无意破坏。

---

## 4. 非目标

本路线暂不承诺：

- 完整复制 Codex CLI 或 Claude Code；
- 默认启用自治 subagent 或 agent team；
- 允许多个代理同时修改同一个 checkout；
- 提供无边界的通用 `parallel_tools` 元工具；
- 默认运行仓库提供的任意 Shell Hook；
- 默认允许浏览器访问任意外部网站；
- 一次性接入所有编程语言的 LSP；
- 为追求理论延迟恢复不稳定的 stateful MCP 默认模式；
- 让项目级配置扩大服务器 allowed roots 或绕过敏感路径保护。

## 5. 核心设计原则

### 5.1 一致性先于新增能力

以下五层必须保持一致：

```text
实际注册工具
= server instructions
= 文档
= Skill 指导
= 测试合同
```

发现漂移时，应先修复真实合同，再添加新工具。

### 5.2 优先减少往返，不堆积微型工具

ChatGPT 通过 LocalSpace 编程时，主要交互链路通常是：

```text
模型决策
→ MCP 请求
→ 网络、OAuth 与 Transport
→ LocalSpace 工具执行
→ 返回结果
→ 模型再次决策
```

因此，应优先建设：

- 批量读取；
- 受控并行验证；
- 紧凑结构化输出；
- 准确 Tool Search；
- 合理的组合工具；
- 可测量的请求和工具指标。

### 5.3 安全操作尽可能并行，有状态操作确定性串行

并行能力不应被理解为“所有工具都同时运行”。默认规则是：

- 独立只读操作可以并行；
- CPU 重型扫描有界并行；
- 不同进程 Session 可以并行；
- 同一进程 Session 的交互必须串行；
- 同一工作区的修改操作必须串行；
- 同一 Git Root 的 Git 写操作和 Review Checkpoint 必须串行。

### 5.4 默认核心与可选工具包分离

默认核心继续覆盖：

- workspace；
- 文件读取和搜索；
- 轻量代码导航；
- patch 编辑；
- 进程；
- Git；
- Diff；
- 基础诊断。

后续高级能力优先作为可选工具包：

- `code-intelligence`；
- `browser`；
- `advanced-policy`；
- `experimental-collaboration`。

### 5.5 项目策略只能收紧权限

项目级策略可以禁止或限制操作，但不能：

- 扩大服务器 allowed roots；
- 绕过敏感路径保护；
- 自动信任仓库提供的任意代码；
- 降低命令风险等级；
- 绕过用户审批。

### 5.6 每个阶段独立验收

每个实现阶段至少执行：

```text
focused tests
→ full tests
→ typecheck
→ build
→ docs review
→ real ChatGPT/MCP acceptance
→ git status verification
```

真实客户端验收未完成时，不得将客户端行为描述为已支持。

消除工具注册、服务器指令、文档、Skill 和测试之间的漂移。

```text
src/tool-catalog.ts
```


## 9. E2 — Performance, Activity, and Request Observability

### 9.1 目标

回答“慢在哪里”，并为并发和批量能力建立可信基线。

### 9.2 E2-T01：MCP 请求阶段耗时

当前状态：实现与自动化验收完成；真实 ChatGPT 验收随服务重启统一补做。

当前实现记录：

- OAuth authentication；
- stateless/stateful MCP Server 构造；
- Transport connect；
- Transport handle；
- stateless cleanup；
- Server total time；
- HTTP status、request/response bytes、RPC method、tool 和 workspace。

由于当前 MCP SDK 不分别暴露 Tool dispatch 与 JSON serialization，
`transportHandleMs` 暂时包含 SDK dispatch、工具执行和响应序列化；工具自身
执行时间继续由 Activity 指标提供。该边界必须在后续报告中保持明确。

记录或聚合以下阶段：

```text
auth
server_create
tool_registration
transport_connect
tool_execution
response_serialization
cleanup
total_request
```

stateless 模式尤其需要区分：

- 每次创建 MCP Server 的固定成本；
- 工具自身成本；
- OAuth 和 HTTP 成本；
- 输出序列化成本。

### 9.3 E2-T02：统一工具指标

当前状态：实现与自动化验收完成；真实 ChatGPT 验收随服务重启统一补做。

已实现：

- success/failure、duration、running、exit code、truncated；
- workspace、tool category、concurrency class；
- process output bytes；
- request/response HTTP bytes；
- 所有注册工具返回的 `content` 与 `structuredContent` UTF-8 字节数；
- queued time 字段和聚合结构已预留，等待 E2.5 调度器接入。

输出指标只记录字节数，不为了指标保留实际文本、图像数据或 structured
payload。queued time 在 E2.5 调度器接入前保持 0，这是明确的阶段边界。

工具指标至少包含：

- 成功、失败、blocked；
- queued time；
- execution time；
- running；
- output size；
- structured output size；
- truncated；
- workspace；
- tool category；
- concurrency class。

不得默认记录完整文件内容或敏感命令。

### 9.4 E2-T03：活动记录与持久安全审计分层

当前状态：实现与自动化验收完成；真实 ChatGPT 验收随服务重启统一补做。

实现边界：

- 新增有界 `ToolActivityLogManager`，记录所有近期工具活动；
- 活动记录按可信工具目录补充 category 和 concurrency class；
- 普通 read/search/navigation 活动只进入内存，不写入 `audit.jsonl`；
- 现有文件修改、Shell、Git 写、安全审批和 blocked 事件继续使用 Durable Audit Log；
- 活动环容量暂复用 `LOCALSPACE_AUDIT_MAX_MEMORY_EVENTS`，不新增配置项。

建议分为：

#### 内存 Activity Ring Buffer

- 记录所有近期工具；
- 用于 `session_summary`；
- 有界保留；
- 服务重启后允许丢失。

#### Durable Audit Log

- 文件修改；
- Shell 命令；
- Git 写操作；
- blocked 和 approved；
- 安全风险；
- 关键认证和生命周期事件。

这样可以提高 `session_summary` 完整性，同时避免普通读取造成持久日志快速增长。

### 9.5 E2-T04：扩展 `session_summary`

当前状态：实现与自动化验收完成；真实 ChatGPT 验收随服务重启统一补做。

当前实现增加：

- 所有近期工具调用和按工具聚合；
- category 与 concurrency class 聚合；
- 成功、失败、running、truncated 和 process poll 计数；
- 平均/最大执行时长；
- 预留 queued time 聚合字段，E2.5 调度器接入后填充；
- Durable Audit 事件数、blocked、approved、commands、risks 和近期安全事件。
- Workspace 级 MCP request count、RPC/tool 分布、request/response bytes，以及
  auth/server-create/connect/handle/cleanup/total 分段耗时。

建议增加：

- 所有近期工具调用；
- 每工具调用次数；
- 成功率；
- 平均和最大耗时；
- 排队耗时；
- 截断次数；
- 进程轮询次数；
- 读、写、Git 和进程分类。

优先扩展现有工具，不新增默认 `performance_summary`。

### 9.6 E2-T05：基准脚本

当前状态：实现与自动化验收完成；基准 Schema 已升级到 v2。

当前脚本除客户端 Loopback 时间外，还通过 `session_summary` 输出服务端观察到
的 request phase 聚合。2026-07-21 的本机开发态样本显示：OAuth 与 Transport
connect 开销很小，stateless Server 构造约为数毫秒；长进程轮询的主要时间位于
`transportHandle`。该样本不包含 ChatGPT 模型延迟、公网 Tunnel 或浏览器渲染。

建议新增：

```text
scripts/benchmark-mcp.mjs
```

覆盖：

- loopback；
- 可选公网 URL；
- initialize；
- `tools/list`；
- 并发 `tools/list`；
- `open_workspace`；
- `read`；
- `grep`；
- `project_map`；
- 两个独立 `exec_command`；
- 同一 Session 并发轮询保护测试。

输出人类可读摘要和机器可读 JSON。

### 9.7 E2 验收

当前自动化验收状态：通过。

## 10. E2.5 — Bounded Tool Concurrency Foundation

当前状态：实现与自动化验收完成；真实 ChatGPT 原生并行和公网行为随服务重启统一补做。

当前实现边界：

- 所有注册工具取得全局 Tool Permit；
- shared/heavy read 使用 Workspace 共享锁；
- LocalSpace mutation 使用 Workspace 独占锁；
- Git 写按 Git/Workspace Root Mutex → Workspace 独占锁顺序执行；
- heavy scan 使用独立 Semaphore；
- 同一 Process Session 的交互确定性串行；
- Child Process 同时受全局和 Workspace 进程额度约束，Permit 持有到进程退出；
- `open_workspace(mode=worktree)` 使用全局独占执行锁；
- Activity 指标记录真实 `queuedMs`；
- 任意 `exec_command` 是否会写共享资源仍不可自动证明，不声明为冲突安全。

### 10.1 目标

在增加 `read_many` 和 `run_checks` 前，为 LocalSpace 建立明确、有界、可审计的并发语义。

并行实现必须同时满足：

- 性能收益可测量；
- 写操作没有丢失更新；
- Git 状态和 Review Checkpoint 语义确定；
- 进程输出不会被错误消费者取走；
- 并发上限不会造成资源耗尽；
- ChatGPT 是否原生并行不会影响核心能力正确性。

### 10.2 当前可行性边界

当前架构已经证明：

- stateless HTTP/MCP 请求能够并发处理；
- 现有测试可同时执行多个 `tools/list`；
- 一个 `ProcessSessionManager` 可以管理多个独立子进程；
- `code_map` 已使用内部 `Promise.all` 并行执行只读子任务。

当前尚未提供：

- 全局工具 Semaphore；
- Workspace 读写锁；
- Git Root 独占锁；
- Process Session Mutex；
- CPU 重型扫描并发限制；
- 每工作区进程上限；
- 明确排队和取消语义。

### 10.3 并发分类

建议定义：

```ts
type ToolConcurrencyClass =
  | "shared-read"
  | "heavy-read"
  | "workspace-write"
  | "git-write"
  | "process-start"
  | "process-session"
  | "global-exclusive";
```

候选映射：

| 工具 | 并发分类 | 默认语义 |
| --- | --- | --- |
| `read` | `shared-read` | 同一工作区可并行 |
| `grep`、`glob`、`ls` | `shared-read` | 同一工作区可并行 |
| `project_map`、`entrypoints` | `shared-read` | 同一工作区可并行 |
| `symbols`、`imports`、`references`、`code_map` | `heavy-read` | 有界并行 |
| `workspace_info`、`doctor`、`session_summary` | `shared-read` | 可并行 |
| `git_status`、`git_diff`、`git_log` | `shared-read` + Git Root 读 | 无 Git 写时可并行 |
| `apply_patch` | `workspace-write` | 同一工作区独占 |
| `show_changes` | `workspace-write` + `git-write` | Workspace 和 Git Root 独占 |
| `git_add`、`git_commit` | `git-write` | 同一 Git Root 独占 |
| `exec_command` | `process-start` | Open-world 命令；只保证有界启动，不自动保证文件系统无冲突 |
| `write_stdin` | `process-session` | 同一 Session 串行，不同 Session 可并行 |
| worktree 创建 | `git-write` | 同一 Git Root 串行 |

工具分类必须来自可信工具目录，不根据模型输入或描述文本动态推断。

`exec_command` 需要单独对待。命令可能只读，也可能写入源码、构建产物、Coverage、数据库或临时文件。第一阶段不尝试从任意 Shell 文本证明命令的完整读写集合：

- 调度器只限制全局和每工作区进程数量；
- 高风险命令审批保持不变；
- 并行启动多个命令必须由调用方确认它们可以安全共存；
- LocalSpace 不把两个通用命令同时成功启动解释为它们在语义上互不冲突；
- `run_checks` 通过受控输入、结果标记和工作区修订检测提供更明确的并行验证语义。

### 10.4 E2.5-T01：全局并发限制

建议增加配置，最终默认值需由 E2 基准确定。初始候选值：

```text
LOCALSPACE_MAX_CONCURRENT_TOOL_CALLS=8
LOCALSPACE_MAX_CONCURRENT_SCANS=2
LOCALSPACE_MAX_CONCURRENT_PROCESSES=4
LOCALSPACE_MAX_WORKSPACE_PROCESSES=2
```

要求：

- 配置有安全上下限；
- `doctor` 展示最终值；
- 超过上限时排队，不无边界创建任务；
- Server shutdown 能取消等待者；
- 客户端断开时尽可能停止无意义等待。

### 10.5 E2.5-T02：Workspace 读写锁

每个 Workspace 建立异步 Read/Write Lock。

#### Shared Read Lock

多个只读工具可以同时进入。

#### Exclusive Write Lock

以下操作持有独占写锁：

- `apply_patch`；
- 任何后续写文件工具；
- `show_changes`；
- 需要工作区一致快照的 Git 写操作。

写操作期间，读操作也等待。原因是多文件 Patch 当前不是整个工作区级别的原子事务，读取进入可能观察到部分更新状态。

### 10.6 E2.5-T03：锁顺序与死锁预防

任何同时需要多个锁的操作必须使用统一顺序：

```text
Global tool permit
→ Git Root lock
→ Workspace lock
→ Process Session lock
```

规则：

- 不允许在持有后序锁时再回头申请前序锁；
- 不使用隐式锁升级，Shared 转 Exclusive 时应释放后重新按顺序申请；
- 多个 Git Root 或 Workspace 锁按规范化路径排序后申请；
- 排队超时或取消时必须释放已获得的所有锁；
- 测试必须覆盖取消、异常和 Server shutdown 后无遗留锁。

### 10.7 E2.5-T04：Git Root 锁

不同 Workspace ID 可能指向同一 Git checkout，因此仅按 Workspace 锁不足够。

以下操作按真实 Git Root 使用独占锁：

- `git_add`；
- `git_commit`；
- `show_changes`；
- worktree 创建和后续删除；
- 未来 branch、merge、reset 等 Git 写操作。

Git 只读查询可以共享，但必须与 Git 写操作互斥，以避免状态来自不一致时间点。

### 10.8 E2.5-T05：Process Session 锁

锁键：

```text
workspaceId + sessionId
```

同一 Session 的以下操作严格按进入顺序执行：

- poll；
- stdin write；
- resize；
- Ctrl-C；
- 未来 terminate。

不同 Session 互不阻塞。

当前 `write_stdin` 会 drain 输出缓冲，因此不允许两个消费者同时轮询同一 Session。

### 10.9 E2.5-T06：Heavy Read 限制

`symbols`、`imports`、`references` 和 `code_map` 当前包含较多同步 TypeScript 解析。`Promise.all` 不能让主线程 CPU 工作真正并行，过多扫描可能增加 Event Loop 延迟。

第一阶段：

- 全局 heavy-read 并发默认上限 2；
- 对大仓库保留文件和结果上限；
- 记录 Event Loop 和工具耗时；
- 暂不引入 Worker Threads。

只有基准证明主线程解析成为关键瓶颈时，再单独设计 Worker Pool。

### 10.10 E2.5-T07：排队、超时和取消

工具结果和活动指标应能区分：

```ts
{
  queuedMs: number;
  executionMs: number;
  concurrencyClass: ToolConcurrencyClass;
}
```

需要定义：

- Queue timeout；
- Server shutdown cancellation；
- Client abort；
- 等待 Workspace 写锁或 Git Root 锁的错误信息；
- 被取消任务是否写入活动记录和审计。

### 10.11 E2.5-T08：并发测试矩阵

至少覆盖：

#### 应成功并行

- 多个独立 `read`；
- `read` + `grep` + `project_map`；
- 不同 Workspace 的只读工具；
- 两个经过确认互不冲突的独立 `exec_command`；
- 不同 Session 的 `write_stdin`；
- 多个并发 `tools/list`。

#### 应排队或串行

- 同一 Workspace 的两个 `apply_patch`；
- `apply_patch` 与 `read`；
- 同一 Git Root 的 `git_add` 与 `git_commit`；
- 两个 `show_changes`；
- 同一 Session 的两个 `write_stdin`；
- worktree 创建与 Git 写操作。

#### 应验证无状态损坏

- 并发 Patch 不发生丢失更新；
- `show_changes` checkpoint 不跳过或重复错误范围；
- Git Index 不产生遗留锁；
- 进程输出只被一个有序消费者 drain；
- 多锁操作遵守统一取锁顺序且异常后无遗留锁；
- 审批 Token 仍保持一次性和上下文绑定。

## 11. E3 — Bounded Batch File Reads

当前状态：实现与自动化验收完成；真实 ChatGPT Tool 选择验收随服务重启统一补做。

当前实现边界：

- `read_many` 仅加入 `codex` 和默认 `hybrid` Tool Surface；
- 每次 1–20 个已知文件，输入顺序稳定；
- 内部并发固定上限 4，整个 Tool Call 仍受 E2.5 Workspace 共享读锁保护；
- 单文件失败不影响其他文件；
- 总文本默认 50,000 字符，最大 200,000；单文件最多返回 50,000 字符；
- 图片作为单文件失败并提示使用 `read`；
- 所有路径预先按 `resolveReadPath` 检查，Skill 不允许在同一批次中通过读取
  `SKILL.md` 后立即解锁其他支持文件；
- 历史 v1.0.6 工具面基线保持不变，v1.1 新增项单独记录。

### 11.1 目标

将多个已知文件的串行读取缩短为一次 MCP 调用，并在 LocalSpace 内部提供有界并行。

### 11.2 输入设计

建议：

```ts
{
  workspaceId: string;
  files: Array<{
    path: string;
    offset?: number;
    limit?: number;
  }>;
  maxTotalCharacters?: number;
}
```

文件数、单文件输出和总输出均必须有界。

### 11.3 返回设计

一个文件失败不应导致全部读取失败：

```ts
{
  results: Array<{
    path: string;
    success: boolean;
    text?: string;
    error?: string;
    truncated?: boolean;
    lineCount?: number;
  }>;
  summary: {
    requested: number;
    succeeded: number;
```

### 11.4 安全边界

必须复用：

- 嵌套指令规则；
- 路径规范化；
- Activity 记录。

批量读取不能绕过先读 `SKILL.md` 后读取 Skill 附属文件的规则。

### 11.5 内部并行

建议：

- 整个调用持有 Workspace shared-read lock；
- 默认单次内部并发 4；
- 使用有界 `mapWithConcurrency`，不直接无边界 `Promise.all`；
- 返回顺序与输入顺序一致；
- 使用部分成功语义；
- 总字符预算优先保证每个文件至少返回错误或摘要。

### 11.6 Skill 更新

`localspace-code-navigation` 应指导：

- 已知多个具体文件时使用 `read_many`；
- 未知文件时先使用搜索和符号工具；
- 不用 `read_many` 替代无边界仓库扫描。

## 12. E4 — Bounded Package Check Runner

当前状态：实现与自动化验证完成；真实 ChatGPT 验收等待统一重启；E5 next。

当前实现边界：

- `run_checks` 仅加入 `codex` 和默认 `hybrid` Tool Surface；
- 只接受当前 Workspace `package.json` 中存在的 1–8 个脚本名；
- 包管理器从 `packageManager` 或 lockfile 识别，默认 npm；
- 默认并发 2，最大 4，所有子进程继续受 E2.5 全局/Workspace 生命周期额度约束；
- `failFast` 只阻止尚未启动的 Check，已运行 Check 正常收尾；
- 危险脚本按实际 script 内容分析，并以原子批量审批处理；
- 长任务使用负数 Check Group Session ID，通过现有 `write_stdin` 轮询或 Ctrl-C；
- Check Group 不接受任意 stdin 或 PTY resize；
- 返回每项输出/状态、聚合 Summary、排队时间和 Workspace revision 前后值；
- Validation Summary 同时识别 `exec_command` 和 `run_checks` Durable Audit 事件；
- 不提供任意命令批量器。

### 12.1 目标

减少多项独立验证的启动和轮询往返，同时保持命令安全和结果可追溯。

### 12.2 不采用通用任意命令批量器

第一版不提供：

```ts
run_checks({ commands: ["任意命令", "任意命令"] })
```

这会形成并行任意 Shell，扩大安全面。

### 12.3 推荐输入

第一版仅运行项目声明的 package scripts：

```ts
{
  workspaceId: string;
  checks: string[];
  concurrency?: number;
  failFast?: boolean;
}
```

典型检查名称：

- `typecheck`；
- `lint`；
- `test`；
- `build`。

自定义命令继续使用 `exec_command`。

### 12.4 进程组设计

抽象 Process Group Session，同时复用 `write_stdin`：

```text
run_checks
→ sessionId
→ write_stdin poll/cancel
```

不额外增加多个轮询工具。

### 12.5 并发和资源控制

候选默认：

- `concurrency = 2`；
- 最大值 4；
- 每工作区进程上限受 E2.5 控制；
- 默认不 fail-fast；
- 每项检查独立状态、退出码和输出预算；
- Ctrl-C 终止整个检查组。

Package scripts 仍可能写入 `dist`、Coverage、缓存、数据库或临时目录，因此 `run_checks` 不能将并发验证描述为天然无冲突。第一版要求：

- 仅并行运行调用方明确选择的检查；
- 文档列出常见共享输出目录风险；
- 同名检查不得重复并发；
- 可以为项目策略增加禁止并行的脚本列表；
- 并发失败时保留每项独立输出，不自动用串行重试掩盖问题。

### 12.6 命令安全

即使脚本来自 `package.json`，仍必须：

- 解析实际脚本；
- 执行 command safety 分析；
- danger 级别仍要求 approval；
- 不因脚本名称是 `test` 就自动信任；
- 记录每个子命令风险和审批状态。

### 12.7 工作区修订检测

检查组开始和结束时记录工作区修订摘要。如果运行期间工作区发生变化，结果必须注明：

```text
检查命令成功，但结果可能基于较早的工作区状态。
```

不能将该结果直接描述为当前工作区最终验证通过。

### 12.8 返回结构

候选：

```ts
{
  running: boolean;
  sessionId?: number;
  checks: Array<{
    name: string;
    status: "queued" | "running" | "passed" | "failed" | "cancelled";
    exitCode?: number;
    wallTimeMs?: number;
    outputTruncated?: boolean;
  }>;
  workspaceChangedDuringRun: boolean;
}
```

### 12.9 E4 验收

- 多项独立检查有界并行；
- `write_stdin` 可轮询和取消检查组；
- 每项结果独立；
- 高风险脚本不绕过审批；
- 工作区变化能够识别；
- 相比串行 `exec_command` 明显减少 MCP 往返；
- 不破坏现有单进程 Session。

自动化验收结果（2026-07-21）：

- focused approval、package-check、Check Group、Validation Summary、Tool Surface、输出 Schema 和真实 stateless MCP 测试通过；
- `npm test`、`npm run typecheck` 和 `npm run build` 通过；
- 真实 stateless MCP 验证了并行成功、长检查组轮询、Ctrl-C 边界和危险脚本审批；
- 两个基于同一 Workspace 的独立 package scripts 能通过 `run_checks(concurrency=2)` 并行；
- 精确提交 `1ff5e82` 的正式本机 Loopback 基准中，两个各包含 1 秒任务的 package scripts：两次串行 `exec_command` 为 `3561.49ms`，一次 `run_checks` 为 `2661.87ms`，客户端观察耗时减少约 `25.3%`；
- 完整样本保存在 `docs/baselines/v1.1-e4-run-checks-benchmark.json`；
- Workspace revision 会覆盖 HEAD、暂存/未暂存 Diff 和未跟踪文件内容；被 Git 忽略的缓存或构建产物不纳入该修订摘要；
- 该数字是单机单次样本，不代表公开网络、其他操作系统或真实项目的固定性能承诺；
- 真实 ChatGPT 是否主动选择 `run_checks` 仍待以后统一重启服务后验收。

## 14. E6 — Optional TypeScript/JavaScript Code Intelligence

### 14.1 目标

弥补轻量 AST 扫描在大型重构上的不足。

### 14.2 工具包边界

候选配置：

```text
LOCALSPACE_TOOL_PACKS=code-intelligence
```

第一阶段只支持 TypeScript/JavaScript，不声明其他语言受支持。

### 14.3 候选能力

- `diagnostics`；
- `definition`；
- `implementations`；
- `rename_preview`。

`rename_preview` 只生成修改预览，不直接写文件。实际修改继续通过 `apply_patch` 或后续明确审批流程。

- definition 和 implementation 有可靠测试；
- rename preview 不直接修改文件；
- 不支持语言明确返回 unsupported；
- 关闭工具包后核心工具面不变化。

## 15. E7 — Browser Debugging Evaluation

### 15.1 目标

先评估方案，不直接承诺 LocalSpace 内置浏览器能力。

### 15.2 候选方案

#### A. 独立 Playwright MCP

优点：成熟、避免重复实现、浏览器生命周期独立。

缺点：需要第二个 MCP，Workspace 和浏览器状态分离。

#### B. LocalSpace Browser Pack

候选能力：

- `browser_open`；
- `browser_snapshot`；
- `browser_click`；
- `browser_fill`；
- `browser_screenshot`；
- `browser_console`。

优点：开发闭环统一。

缺点：依赖、攻击面、浏览器生命周期和工具数量明显扩大。

#### C. Skill + `exec_command`

优点：不增加核心代码，现阶段可用。

缺点：结构化输出、页面状态和截图反馈较弱。

### 15.3 决策标准

只有真实前端任务证明方案 C 明显不足时，才实施 Browser Pack。

### 15.4 安全边界

若实施内置浏览器：

- 默认只允许 localhost；
- 外部 origin 需 allowlist；
- 文件上传需显式路径授权；
- 下载使用受控临时目录；
- 不读取用户日常浏览器 Profile；
- 默认独立浏览器上下文；
- 不自动复用个人登录状态。

## 16. E8 — Policy and Deterministic Automation

### 16.1 项目策略

候选文件：

```text
.localspace/policy.json
```

可支持：

- 只读目录；
- 禁止命令模式；

- 强制审批工具；
- 最大批量读取数量；

策略只能收紧服务器权限。

### 16.2 Hooks

第一阶段不支持任意 Shell Hook。优先内部确定性规则：

- 修改后建议格式化；
- commit 前检查 validation 状态；
- 敏感文件变化强制提示；
- package metadata 修改后建议 package dry-run。

### 16.3 E8 验收

- 项目策略不能扩大服务器权限；
- 恶意仓库不能修改自身信任等级；
- 解析失败时采用更严格规则；
- Hook 不能绕过 command approval；
- 策略决策有活动或审计记录。

## 18. 不采用的并行设计

### 18.1 不提供通用 `parallel_tools`

不计划增加：

```ts
parallel_tools({
  calls: [
    { tool: "apply_patch", args: {} },
    { tool: "git_commit", args: {} }
  ]
})
```

原因：

- Schema 复杂；
- 容易模糊审批边界；
- 工具依赖难以推导；
- 写冲突恢复困难；
- 用户界面难以清晰展示；
- 可能绕过单工具的明确安全语义。

### 18.2 不依赖 ChatGPT 原生并行作为唯一方案

ChatGPT 或其他主机可能在一轮中并行调用独立 MCP 工具，但具体行为不由 LocalSpace 控制。

因此：

- 原生并行可作为额外加速；
- `read_many` 和 `run_checks` 提供 LocalSpace 可保证的批量收益；
- 服务端并发控制保证无论客户端是否并行，状态都正确。

## 21. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 工具目录重构导致注册回归 | 客户端缺少工具 | 各模式精确合同测试 |
| 指标增加日志噪声 | 磁盘增长和隐私风险 | Activity 与 durable audit 分层 |
| 并发写造成丢失更新 | 代码损坏 | Workspace 独占写锁 |
| 多 Workspace 指向同一 Repo | Git Index 冲突 | 按真实 Git Root 独占锁 |
| 同 Session 多轮询 | 输出被错误 drain | Process Session Mutex |
| AST 扫描过多 | Event Loop 延迟 | Heavy-read Semaphore |
| 并行检查争用资源 | 构建或测试不稳定 | 默认并发 2、资源上限、明确结果 |
| 检查期间代码变化 | 误报验证通过 | Workspace revision 检测 |
| Tool Schema 继续膨胀 | 模型选错工具 | 默认核心有界、工具包可选 |
| 过早声明 supported | 用户误判能力 | 自动化 + 真实客户端验收双门禁 |
